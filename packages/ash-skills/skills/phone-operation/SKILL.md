# 在手机上办事

这里的词都在主人的手机上：`capability_call {member: "device:<手机的 id>", word, body}`。手机的 id 从每轮上下文里的设备列表拿（名字是手机、能力里有 `screen.*` 的那一只），不要写死。列表里没有它，或显示 offline，先读技能 `connect-device`。

## 先分清要哪种

每一轮上下文里有一段「Ash screen execution decision」，已经替你判断了这一轮用哪块屏。照它做，不沿用旧轮次的选择。

| 模式 | 意思 | 怎么做 |
|---|---|---|
| `foreground_handoff` | 主人要的是**把应用打开给他用**（「帮我打开闲鱼」「带我去设置」） | `apps.open` / `settings.open` / `apps.open_url`（链接或深度链接）在真实屏幕上打开，成功后就停，留在那个应用里；不要用虚拟屏冒充已打开，不要自己回 Ash 或回桌面 |
| `virtual_task` | 主人要你在应用**里面办事**并拿结果（「在闲鱼查一下价格」），他留在 Ash 里 | `vscreen.create` → `vscreen.launch` → `vscreen.see` → 用 `vscreen.tap/swipe/key/type` 操作，做完 `vscreen.close` |
| `foreground_task` | 要在真实屏幕办事，或需要主人自己登录、收验证码 | 用 `screen.*` 操作真实屏幕；需要他动手时把那一页留着并说明，最后一屏也留着 |
| `no_preference` | 不需要屏幕 | 别无谓地开屏；以后要给主人打开应用仍然用真实屏幕 |

在前台模式下用 `vscreen.*`（除了 `status`、`see`、`close`）会被拒绝，一个操作也不会执行。虚拟屏需要主人接上「后台也能动手」（手机的调试身份，Android 10 以上），`vscreen.status` 或 `config.status`（`host_shell` 一项）可以先看；用不了就按前台办，并告诉主人原因。手机重启后要主人自己重新接一下，Ash 不能替他开关无线调试。

## 先看，再点，再看

1. **看**：`screen.read` 列出前台应用、屏幕上有文字或可点的元素，带中心点 `@(x,y)`（可直接作为 `screen.tap` 的 x/y）；游戏和自绘界面读不到东西，改用 `screen.see`（截图，可加 `grid: 4|8` 帮你定位，坐标用 `fx/fy` 比例最稳）。虚拟屏只能 `vscreen.see`，没有元素列表，坐标是虚拟屏的像素，看说明里的换算系数。
2. **点**：`screen.tap {text}` 按文字或描述点，比坐标稳（走无障碍点击，浮窗下也行）；不得已才用 `fx/fy`。
3. **输入**：先点输入框让它获得焦点，再 `screen.type`；普通应用默认整段替换（`mode: "set"`），网页和 WebView 输入框用 `mode: "paste"`。它**不会按回车或发送**，输完要自己点发送按钮。中文走无障碍输入，虚拟屏里中文走剪贴板（会替换主人的剪贴板内容）。
4. **再看**：每一步之后重新 `screen.read` 或 `see`，确认真的到了你以为的那一页再做下一步。一次只做一个动作，页面变了就重新看，不凭旧坐标操作。
5. 每个调用都填 `purpose`：一句主人看得懂的话（「正在查找闲鱼里的订单」），不写命令和参数。

## 卡住了怎么办

- 找不到元素：`screen.scroll {direction}`（`down` 是看更下面的内容）再读；还不行用 `screen.see` 对着图找。
- 被弹窗、键盘、广告挡住：`screen.global_action {action: "back"}` 关键盘或返回；`home`、`recents` 回桌面和切应用。同一个办法最多试 3 次，换思路。
- 页面没反应：等一下再读；仍然不对，退回上一步重来，不要连点。
- 密码、支付页面是安全屏，截图会失败：不是故障，请主人自己来。
- 无障碍断了、`screen.*` 不可用：先 `config.status` 看是哪一项没开，再 `config.permission.request {name: "accessibility"}` 打开系统设置页，请主人亲手打开（无障碍是主人在系统里开关的，Ash 不能替他开），不要假装做了。
- 其他权限（位置、通知、悬浮窗、后台也能动手、使用情况访问……）同样：`config.status` 看，缺哪项就 `config.permission.request {name}`，授权由主人本人完成。应用总被系统杀掉，用 `config.keepalive.status` 看厂商的自启动和后台限制，请主人在打开的设置页里自己打开。
- 还是做不成：停下，如实说停在了哪一步、屏幕上现在是什么，让主人决定。

## 登录、验证码、付款：边界

- 密码、验证码、短信码、扫码登录、人脸验证，**不替他做**。把那一页留在真实屏幕上，说「请你输入验证码，好了告诉我」，等他说好再继续。需要登录时不要悄悄把后台任务改成前台。
- 付款、下单、转账、发消息给别人：识别出的付款每次都会弹卡问主人。弹卡后冻结的就是那一次调用；批准后先重新看屏幕，确认还是那一页、金额没变，再 `human_pending_redeem`。
- **被打断后不要重复**：超时、取消、批准过期、结果没回来，都先去看实际状态（订单页、已发消息、余额、支付记录）确认有没有成功，再决定要不要做；绝不凭「好像没成」再提交一次。批量操作（一口气下几单、发几条）更要这样：每做完一个核对一个，不要整批重来。

## 哪些要批准

读屏幕和读信息（`screen.read`、`screen.see`、`apps.list`、`settings.get`、`clipboard.get`、`vscreen.see`……）直接执行。点、输入、滑动、打开应用或设置、按键、在虚拟屏里操作，由裁判当场判断：明显是主人要的就放行，拿不准会弹卡。改系统设置、改剪贴板、创建和关闭虚拟屏属于结构性改动。`shell.run` 这类命令先过审核模型，放行就执行，拿不准才弹卡；设备档位是 `full` 就直接执行。识别出的付款每次都弹卡。依赖当前屏幕的调用，`approval_ttl_minutes` 设 2–5 分钟，批准回来后先重新看一眼屏幕再兑现。不换说法再问同一件被拒绝的事。

## 好的样子

主人说「在闲鱼帮我看看这个耳机多少钱」。上下文判定 `virtual_task`：`vscreen.create` → `vscreen.launch {app: "闲鱼"}` → `vscreen.see` 确认确实出现在虚拟屏而不是主人的屏幕 → 点搜索框、`vscreen.type` 输入、点搜索 → `vscreen.see` 读结果 → 回「查到三个，最低 128 元，卖家……」 → `vscreen.close`。中途弹出登录页，就停下说「需要你在闲鱼里登录一下，我把它放到前面」，改用前台并告诉主人。

主人说「帮我打开设置里的电池页」：`foreground_handoff`，`settings.open {page: …}` 成功后就结束，一句话告诉他已经打开，不再操作。

## 常见错误

- 不看屏幕就凭记忆点坐标。
- 把「打开给他用」做成虚拟屏里打开，主人什么也没看到。
- 输完文字没点发送，就说「已发送」。
- 工具没成功就说「已经打开」「已经付款」。
- 被打断后重新提交订单或付款。
- 替主人输入验证码或密码；或把一个弹卡等待当作失败，另走旁路。
- 做完不关虚拟屏（`vscreen.close`）。

## 怎么核对

每个动作之后用 `screen.read` / `see` / `vscreen.see` 确认结果，再对主人说「好了」。需要结果的任务，把你亲眼看到的写进回复；没看到的就说没看到。
