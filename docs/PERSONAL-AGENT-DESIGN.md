# Ash：个人上下文与行动系统

产品设计草案 v0.1 · 2026-10-09

状态：研究与设计提案。本文不表示功能已经实现，也不承诺任何第三方桌面客户端已经开放所需接口。

## 1. 定位与设计原则

Ash 围绕同一个用户，维护跨设备、跨 Agent、跨时间的上下文，并调用合适的执行能力，持续推进用户的事情。

核心体验：用户表达新的意图时，Ash 能理解前情、定位当前状态、找到可用执行者，并把结果带回这件事情。切换设备、执行工具或会话，不应要求用户重新介绍背景。

设计原则：

- 用户是上下文的拥有者；设备和 Agent 是信息来源与执行参与者。
- 以“事情”为主要组织单位。一次对话、一次执行和一份文件都是事情中的关联记录。
- 概括帮助理解，原始证据支持核实；重要事实必须可追溯。
- 上下文随时间更新，历史决定保留，但只有仍有效的决定指导当前工作。
- 每次执行获得与任务有关且获准使用的上下文，不默认得到全部个人信息。
- 自主性来自用户授权，不能仅凭上下文推测得到。

## 2. 贯穿场景：把一个想法推进到可验收的功能

以下为目标体验示例，不代表现有 Ash 能力。

### 周一早上：手机记录意图

用户对 Ash 说：“给我的应用加一个离线阅读功能，先把方案想清楚，这周希望能自己用。”

Ash 建立一件事情“离线阅读”，记录目标、时间要求和“当前只研究”的约束，关联用户选定的项目。缺失的信息只在影响下一步时询问；不会因为提到了功能就立即开始开发。

### 周一下午：电脑展开研究

用户在已有 Claude 会话中讨论设计，并决定“第一版只缓存文字，不做图片”。

在用户已连接并授权的范围内，Ash 将这段会话关联到“离线阅读”。明确决定进入当前上下文，探索过但放弃的方案保留为历史。对归属不确定的会话，Ash 提议关联，而不直接合并。

### 周二：授权开发并分派执行

用户说：“按昨天的方案做，交给 Codex，先别提交。”

Ash 将“只研究”更新为“允许实现和本地验证，暂不提交”，保留约束变化的时间与原话。它交给 Codex 的工作说明包括目标、当前方案、相关代码位置、已有决定和验收条件。

如果原会话支持接续，则使用原会话；否则在明确告知后，建立关联执行并补充所需上下文。两种方式都归入同一件事情，但不声称拥有相同的运行状态和工具能力。

### 周二外出：手机继续指挥

用户问：“做到哪了？再加一个离线状态提示。”

Ash 汇总最近已确认的执行状态，展示信息时间。若 Codex 正在运行且支持追加指令，则把要求送入当前执行；若不支持，则排入下一轮，明确显示“等待当前执行结束”。重复发送或断线重连不应导致重复执行。

### 周三：手机参与验证

电脑产出测试包后，Ash 在设备能力和用户授权范围内协助手机验证。它将截图、操作步骤和观察到的现象作为证据关联到原事情，再交给执行者修复。

“Agent 报告完成”“测试通过”“用户验收通过”是三个不同状态。没有验证证据时，不能将“实现完成”概括成“功能可用”。

### 周五：隔几天回来

用户说：“继续离线阅读。”

Ash 给出简短接续说明：“文字缓存已完成；手机验证发现重启后列表未刷新；你要求暂不提交。下一步建议修复刷新问题。”

用户无需翻阅多个聊天窗口。开始执行前，Ash 核实分支、文件和设备等容易变化的状态；不会把几天前的执行环境当成当前事实。

## 3. 产品的基本对象

### 用户背景

长期目标、明确偏好、常用工作方式和长期约束。一次临时要求不会自动变成长期偏好；从行为推断出的偏好必须标为推断，并允许用户纠正。

### 事情

一个可持续推进的目标，例如“离线阅读”“准备出差”或“研究一个商业机会”。建议包含：

- 目标与完成标准。
- 当前阶段、下一步、阻塞点。
- 有效决定与约束。
- 参与的设备、Agent、会话、资料和产物。
- 执行历史与验证记录。
- 用户给予的行动权限。

事情可以包含多个子任务。首版以一个主要执行者推进为默认；并行分工应明确各自产物和修改范围。

### 上下文记录

每条记录包括内容、类型、来源、所属事情、发生时间、记录时间、有效状态和使用范围。类型至少区分：明确事实、用户决定、偏好、Agent 推断和执行报告。

有效状态区分当前有效、待核实、已被替代和已过期。新信息与旧信息冲突时，根据来源和用户决定处理；不同事情中的不同约束可以同时成立。涉及关键目标或授权的冲突不能只按时间新旧自动覆盖。

### 执行与产物

执行记录谁在什么设备、项目和会话中完成什么任务，以及接收、运行、等待、失败和完成状态。产物包括文件、代码变更、方案、截图和测试结果。执行失败不等于事情失败；切换执行者也不意味着重新创建事情。

## 4. 上下文的生命周期

1. **获取**：用户主动输入，或从已授权连接读取会话、选定资料和执行事件。首版采用主动关联，之后再研究被动发现。
2. **归属**：判断属于哪个用户目标或事情；不确定时暂存待关联，避免把不同项目混在一起。
3. **提炼**：从原始内容中提取决定、事实、问题、进度和产物，保留来源定位。
4. **更新**：形成事情的当前概括，处理冲突、撤回和过期信息。历史不能悄悄改写。
5. **按需交付**：执行前提供目标、必要背景、有效约束、现状、证据入口、验收要求和授权边界。
6. **回收结果**：执行报告作为新证据进入系统；核实后更新状态，决定下一步或请求用户判断。

摘要是可重新生成的视图。权限、截止日期、关键决定和验收状态需要保留明确字段，不能只存在于一段不断压缩的文字中。

## 5. 协作规则

### 上下文权威与执行权威

Ash 负责汇总用户意图、跨端状态和有效约束。具体执行者负责自己的实时运行状态。Ash 不能仅凭历史摘要判断某条命令仍在运行，也不能把连接失败解释为执行已经停止。

### Agent 选择

优先尊重用户指定；其次考虑已有会话的连续性、所需能力、设备在线情况和成本。能力不满足时说明差异并提出替代方案。对同一仓库的写入默认避免多个 Agent 同时修改重叠内容；必要的并行通过独立工作区和明确合并责任处理。

### 适配能力分级

- 能提交新任务并取回结果。
- 能读取和接续已有会话。
- 能跟进实时进展、追加指令和停止执行。
- 能参与审批、接收外部结果，并与桌面界面保持状态一致。

每个连接按实际验证的能力显示。CLI 接入、桌面已有会话接入和屏幕操作分别核实，不视为等价。

### 断线和跨时间接续

状态区分“设备离线”“执行状态未知”“任务等待设备”和“已确认停止”。连接恢复后先对账，再继续；对于可能已经执行成功的操作，核实结果后再决定是否重试。重新执行前检查文件、权限与有效决定是否变化。

## 6. 用户体验

### 首页：现在需要关注什么

展示正在推进的事情、需要用户决策的事项、最近完成的结果，以及与当前工作有关的设备状态。通知集中于完成、失败、阻塞、关键变化和需要批准的操作；普通进度可主动查看。

### 事情详情：一眼接上前情

顶部固定展示目标、当前概括、下一步和更新时间。下面提供关键决定、产物与验收、执行活动和相关会话。用户可以直接说“继续”“换 Claude 看一下”“暂停到明天”，无需先寻找底层会话编号。

### 个人上下文：可见、可改、可追溯

用户可以查看 Ash 记住了什么、为什么记住、来源是什么，以及最近在哪次执行中使用。支持纠正、停止采集、限制发送范围和删除。删除应覆盖受控存储和派生摘要；已经发送给外部工具的信息不能承诺自动撤回，应明确其去向和可用删除能力。

## 7. 自主行动边界

授权按事情、动作和范围定义，并可撤回或到期。阅读和整理也需遵守数据访问范围。

- 已授权范围内的信息整理与状态更新，可持续进行。
- 用户明确要求的分析、草拟、开发和本地验证，可在约定边界内推进。
- 对外发送、发布、支付、扩大数据访问范围等动作，需要相应授权；既有明确授权不反复询问。
- 目标推断、优先级改变或授权冲突需要用户判断。

密码、API Key 等执行凭据通过独立凭据机制管理；上下文只保存必要引用，不向其他 Agent 分发原始秘密。

## 8. 第一阶段范围与验证

第一阶段建议聚焦单用户、一台电脑、一部手机和一个经验证支持的桌面 Agent。

必须证明：

1. 用户能将一个已有会话关联到一件事情。
2. Ash 能生成带来源的目标、现状、决定和下一步概括。
3. 手机追加要求能准确进入目标执行，状态可被核实。
4. 执行结果和关键决定能回到事情中。
5. 隔一天或切换入口后，无需重新介绍前情即可继续。
6. 新决定能替代旧决定，旧约束不会继续错误地指导执行。
7. 设备断线不会导致虚报完成或重复执行。
8. 不相关或未获准的数据不会被交给执行者。

之后依次研究第二个 Agent 的上下文交接、手机参与验证、跨事情的信息复用和主动推进。第一阶段不以同时接入最多工具为成功标准。

建议观察的指标：用户重复解释前情的次数、接续前的纠正次数、过期上下文引起的错误、完成状态与证据的一致性，以及用户能否解释一次行动为何发生。先建立基线，再设量化目标。

## 9. 待研究的技术与产品问题

- 各桌面产品对现有会话、实时控制、审批和结果订阅开放到什么程度？
- 哪些上下文保存在手机、电脑或自建服务；离线时哪个节点能做什么？
- 原始证据保存多久；来源被删除、移动或失去权限后如何降级？
- 用户愿意持续提供哪些数据，哪些只按事情临时授权？
- 多个 Agent 对同一问题的不同结论，如何呈现给用户并形成新决定？

上述问题需要通过接口研究和小规模场景验证决定，暂不锁定数据库、模型、同步协议或部署架构。
